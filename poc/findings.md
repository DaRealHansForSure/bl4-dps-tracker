Game: Borderlands 4, Steam, `Borderlands4.exe` dated 2026-09-19 (post Sep-18 patch).
SDK: oak2-mod-manager v0.3 "Whiskey Foxtrot" (pyunrealsdk 1.10.0, unrealsdk 3.2.0, Python 3.14), installed 2026-09-20.

Dev-machine changes outside the repo:

## A. SDK loads on current patch: PASS

- unrealsdk, pyunrealsdk, console_mod_menu and keybinds all initialise on the Sep-19 build. Issue #17 did not reproduce here.
- Tilde did nothing on this machine (German layout, and BL4 binds Tilde itself). BL4-specific SDK code overwrites the game's console key when `unrealsdk.console_key` is set, so F6 works. `Input.ini` in the user config folder is ignored by the game.
- The console only opens in the world, not on the main menu.

## B. A hookable function fires per damage instance: PASS, with a different mechanism than planned

- 170 UFunctions with `Damage` in the name exist; 62 plausible ones were hooked. None fired for a gunshot. `log_all_calls` over one shot shows zero weapon/hit/damage functions. BL4 applies damage natively; there is no per-hit function to hook.
- `add_hook` returns True for paths that do not exist. Validate with `unrealsdk.find_object("Function", path)` first.
- What works: `OakPlayerController.RecentlyCausedDamageInstances`, a fixed array of 6 `RecentPlayerCausedDamageInstance` structs (the source of the HUD floating numbers). Written round-robin; each write increments that slot's `RepDirtyFlag` (byte). Diffing dirty flags once per frame from a hook on `/Script/GbxUIUMG.GbxUIUMGTickWidget:BP_TickWidget` (~60-100 calls/s) catches every instance. Keying on anything else (target, location) produces false events when a dead target's weak pointer goes null.
- Struct fields: `TotalDamage` (float), `DamageType` (FGameDataHandle with `bIsDoT`, `ElementalType`, `DamageIconFrameName`, name via repr), `DamagedActor` (weak Actor), `DamageLocation`, `DamageFlags.Flags` (uint32), `DamageSource` (DamageSourceContainer, empty in this replicated copy: `Conv_DamageSourceContainer_String` returns ''), `RepDirtyFlag`.
- `ERecentPlayerDamageFlags` values are bit indexes, not masks: CriticalHit=1 -> `Flags & 0x2`, Healing=2 -> `0x4`, Shield=4 -> `0x10`, Resist=8 -> `0x100`, DontShowCrossHairHitMarker=16 -> `0x10000`. Two more bits are not in the reflected enum but were decoded from three recorded sessions (2026-09-20, 156 events, 33 tracked targets): `0x400` (bit 10) is set on every gun hit and on no grenade or knife hit; `0x4000` (bit 14) is set on exactly the last hit each target receives (33 of 33), i.e. the killing blow. A grenade hitting two cats at once produced two 333.0 events in the same tick, one `0x4000` (that cat died) and one `0x0`. The mod attributes hits without `0x400` to source `other` and records `kill`.
- Weapon attribution: `DamageSource` is empty, so use the weapon in hand at the time of the hit: `pawn.ActiveWeapons.Slots[0].Weapon` (an `OakWeapon`, also present as `pawn.EquippedInventorySlots.items[i].InstancedInventory` for the four weapon slots; slots 4-6 hold Shield, GrenadeGadget, RepairKit). Both arrays are empty right after the controller resolves and fill once the pawn is fully spawned, so read them per hit, not once.
- Weapon label: the `OakWeapon` actor carries no display name and there is no reflected way to get one (probes 4-9, see below). Use `weapon.BodyData._path_name()`, e.g. `/Game/Gear/Weapons/AssaultRifles/VLA/Body_VLA_AR.Body_VLA_AR`, whose `Body_<MFR>_<TYPE>` stem gives manufacturer (VLA Vladof, JAK Jakobs, TOR Torgue, BOR Borg, ...) and type (AR, SM, SR, SG, PS, HW). Plus `weapon.Item.data.InstanceId` (uint32, distinct per item: 277-280 for the four equipped guns) to keep two guns of the same body apart. Session stability of `InstanceId` is unverified; do not build cross-session aliases on it without checking.
- Status effect damage (session 2026-09-20 20:57, radiation SMG): ticks arrive as `DamageType` `Radiation_Status` with flags `0x80` or `0x90` (never the gun bit `0x400`), 25 of them with `bIsDoT` set and 30 more without it, so "status damage" must be recognised by the type name suffix `_Status` as well. `ElementalType` on the `Radiation` handle read as 5 on 66 hits and as 0 on 41, so the element comes from the type name, not the field. The tick carries no source; the mod credits it to the last non-status hit on the same target within 30 s (gun or grenade), which matched the sample (Vladof AR radiation hit 0.2 s before the first tick on that target).
- Vehicles: while driving, `pc.Pawn` is an `OakVehicle` without `EquippedInventorySlots`, and `ActiveWeapons.Slots[0].Weapon` is the vehicle gun (`Body_Vehicle_Weapon_RL`, one instance per seat). The mod hides the table and ignores hits while the pawn is not the character (decided by the presence of `EquippedInventorySlots`, cached per pawn class).
- Manufacturer codes seen so far: VLA Vladof, JAK Jakobs, TOR Torgue, BOR Bor, DAD Daedalus. Unknown codes are shown as-is.
- Unresolved `FGameDataHandle`s: some instances (seen on grenade hits) carry a `DamageType` handle whose fields raise `AttributeError` on access (`unresolved FGameDataHandle has no attribute ...`); `_name` still works and gives `'None'`. Read the fields with `getattr(..., default)`.
- Naming dead ends, so nobody repeats them: `Item.data.Identity` (`GbxGame.InventoryIdentity`) is 216 bytes with zero reflected fields, i.e. opaque native data. No class matches InventoryManager/ItemData/Naming; the item system is `GbxGame.GbxItem`/`GbxItemData`/`InventoryItemHandle`/`GbxInventoryChannel`, with names generated natively from Nexus config (`NexusConfigStoreInventoryNamePart`/`NameStrategy`). The HUD is Coherent (`GbxUICoherent`); `OakUIDataCollector_Weapon`/`_ItemCard`/`_WeaponStatus` have no reflected text properties, and a `log_all_calls` trace over weapon swaps shows no UFunction at all (only animation and camera). Hovering a slot in the inventory fires `ui_script_backpack_C:WeaponSlotFocused` with no item data (widget def, position, audio handle). `InventoryItemBlueprintLibrary.GetSummary_InventoryItemSelectionData` takes an `InventoryItemDefProvider` (`{Handle: GameDataHandle, bInstance, Instance}`), i.e. a loot-selection definition, not a player item. The only name-like getter on the weapon actor is `GetAttachParentSocketName`.
- pyunrealsdk notes from these probes: `UStruct._superfields()` walks the class chain (there is no `_superfield`), `_fields()` and `_properties()` already include inherited members, `find_object` raises `ValueError` rather than returning None, and `GbxDefPtrProperty` values render as `FGbxDefPtr(name, type, {...})` dicts.
- Target health for the overkill note: `DamagedActor.HealthState.HealthTypeStates[]` (per health type: flesh/armor/shield) and `DamageState`. Not yet mapped.
- The pawn object changes on respawn; the controller object persisted across the session but may change on map load. Re-resolve `get_pc()` on any read error.
- Ring overflow: >6 instances in one frame would drop events. Untested (no shotgun available). The HUD has the same limit, so the game probably merges pellets, but verify.

## D. Buffer + background flush, no stutter: PASS

`poc/dmgpoc/` implements the mechanism: per-frame diff -> list append -> daemon thread appends JSONL every second to `sdk_mods/settings/dmgpoc.jsonl`. Run on 2026-09-20 (19:08-19:10 local): user loaded in, fought wildlife for about 45 s of damage, idled, then killed `Borderlands4.exe` from Task Manager.

- Mod counters at the last status line: 35 events, 0 errors, 6537 ticks. The JSONL holds exactly 35 complete lines, none truncated. Zero loss.
- Last hit at 17:09:42.46Z, file mtime 17:09:43.31Z: the batch reached disk 0.85 s after the hit, i.e. inside the 1 s flush interval. The writer never built a backlog (every status line's event count matched the file).
- Tick rate stayed at 78-95 hook calls per second for the whole session; the per-frame diff plus `_read_slot` did not show up as a hitch in the numbers. Stutter as felt in play: none, the game felt normal.
- The kill came 20+ s after the last hit, so it did not exercise the worst case directly; the 1 s flush cadence bounds the loss structurally and the writer thread is a daemon, so a hard kill can only lose the current unflushed second.
- Side finding: the one-off weapon layout dump ran at controller-resolve time, when `ActiveWeapons.Slots` and `EquippedInventorySlots.items` were both still empty, so every event carries `"weapon": "unknown"`. `poc/probe_weapon.py` repeats that dump on demand once weapons are equipped; run it in the next session before building weapon attribution.
- Data sanity: 7 of 35 hits flagged crit (flags bit 1), all `elem` 0 and `kind` direct, which matches a non-elemental gun against wildlife. Flag values seen: 1024, 1026, 16384, 17408, 17410 (bits 10, 1, 14 plus combos), still undecoded.

## E. On-screen readout from Python: PASS

Added on 2026-09-20 (the numbers belong in the game, not only in the offline report). Two mechanisms checked with `poc/probe_ui.py`:

- Canvas text via a `/Script/Engine.HUD:ReceiveDrawHUD` hook: dead. `pc.MyHUD` is an `OakHUD`, but the event never appears in a 234k-line `log_all_calls` trace, so BL4's HUD (Coherent UI) never calls it.
- Runtime UMG: works. `WidgetBlueprintLibrary.Create(pc, container_class, pc)` with a concrete native `UserWidget` subclass as container (`UserWidget` itself is abstract; `GbxUIUMGListViewItemWidget` worked, `GbxUIUMGUserWidget` is the cleaner-looking candidate, untested), then `unrealsdk.construct_object("TextBlock", widget.WidgetTree, "DmgTrackerText")`, `widget.WidgetTree.RootWidget = text_block`, `text_block.SetText("...")`, `widget.AddToViewport(10000)`, `widget.SetPositionInViewport(make_struct("Vector2D", X=120, Y=320), True)`. The text rendered above the game HUD in the default 24 pt engine font; `RemoveFromParent()` takes it away. Visibility came back as `SelfHitTestInvisible`, so it does not eat clicks. pyunrealsdk returns `Ellipsis` for void UFunction calls.
- Table rendering (`poc/probe_table.py`, approved on 2026-09-20): root `Border` (`SetBrushColor(LinearColor 0,0,0,0.6)`, `SetPadding(Margin 14,8,14,8)`) containing a `GridPanel`; one `TextBlock` per cell added with `grid.AddChildToGrid(cell, row, column)`, the returned `GridSlot` takes `SetPadding(Margin)` for column gaps (44 units left of every column but the first, 2 above and below). Working `TextBlock` calls: `SetFont(make_struct("SlateFontInfo", FontObject=find_object("Font", "/Engine/EngineFonts/Roboto.Roboto"), Size=30, TypefaceFontName="Regular"))`, `SetJustification(2)` (right), `SetMinDesiredWidth(units)` (320/240/190/140 for Weapon/Total/DPS/Share), `SetColorAndOpacity(make_struct("SlateColor", SpecifiedColor=LinearColor, ColorUseRule=0))`, `SetShadowOffset(Vector2D 1.5,1.5)`, `SetShadowColorAndOpacity(LinearColor 0,0,0,0.8)`. A spacer row is a row of empty cells at font size 10. Colours used: header grey (0.75), weapon in hand yellow (1, 0.85, 0.3), other rows white, total row light blue (0.6, 0.85, 1). `GbxUIUMGUserWidget` works as the container (preferred over the list item widget). Font size 18 was far too small in a ~1100 px wide window (UMG DPI scaling); 30 reads well.
- Hiding in menus (`poc/probe_menu.py`): `pc.bShowMouseCursor` is `True` while the ESC menu, the inventory or the map is open and `False` in play; it flips on the same frame. `GameplayStatics.IsGamePaused(pc)` and `pc.CanOpenStatusMenu()` track it too, the pause flag with up to a second of lag. `pc.IsPaused()` does not exist here.
- Hiding in tunnel transitions (second sampling run, 2026-09-20 20:47): during the transition `pc.IsMoveInputIgnored()` and `pc.IsLookInputIgnored()` are `True` (about 14 s) and `pc.Pawn.bHidden` is `True` for the middle 12 s of it; the cursor flag stays `False`. Hide rule for the readout: no pawn, or `pc.bShowMouseCursor`, or `pawn.bHidden` (all field reads, every frame), or `pc.IsMoveInputIgnored()` (a function call, checked at the 250 ms refresh).
- Damage-to-weapon links (`poc/probe_source.py`, 2026-09-20 21:20-21:32): the ring entry's `DamageSource` container is empty for every hit (string, tags and source blank), dead end. The Torgue gun's explosive rounds are `OakProjectile` actors (`Proj_Arctic_*`); `/Script/GbxGame.projectile:Explode` fires on them within 50 ms of the unflagged damage, in either order, and `GetOwner()` on the projectile returns the `OakWeapon` actor that fired it, `GetInstigator()` the character. A grenade (`tediore_grenade_PredatorDrone`, a `ModularGrenade`) fires the same `Explode` with the character as owner; `GrenadeGadget:ExplodeCallback` likewise. The drone gadget keeps firing missiles for seconds (`LightProjectileScript:OnImpact` on the script CDO, no owner). The melee trick `Script_LTrick_HandleOffhand_C:OnBegin_Const` has the character as associated actor; the knife's three 270.7 hits landed 2.9 s after the swing started. Sticky rounds emit no event at all: they detonate when the gun is swapped away and the ring shows the detonation, gun-flagged, with the new gun already in hand (24.1 stick at +21.92 s with the Torgue in hand, 240.8 detonation at +22.89 s with the sniper in hand). The gun flag therefore marks bullet impacts and sticky detonations, not "all damage of the gun".
- Reading hook arguments is unsafe: v1 of that probe read the `ThrowGadget` arguments inside a PRE hook and crashed the game (access violation reading 0x20, an empty inline struct parameter). Hooks in the mod read the object and call no-argument getters only.
- Tricks (probes 2026-09-20 22:00-22:06, Siren and Exo-Soldier): every trick of every actor starts through `/Script/GbxGame.GbxTrickScript:OnBegin_Mut` and ends through `OnEnd_Mut`. The player's knife runs `ATrick_Melee_Hit_Script_Const_C` (or `ATrick_Melee_PS_Miss...` for a miss): a shared, stateless script whose outer is the package and whose `GetAssociatedActor()` is None, so it cannot say whose swing it is, but enemy melee tricks are named `TRAnim_<Enemy>_..._Melee...` and are instanced on the enemy's character. The `ATrick_Melee` prefix therefore marks the player's own melee. `Script_LTrick_HandleOffhand_C` (under `Tricks/Skills/`) fires on other off-hand actions too and is not a melee signal. Action skills run tricks with `ActionSkill` in the class name (the Siren's Phase Echo Reaper: `Trick_DarkSiren_ActionSkill_PhaseEcho_Reaper_Left/Right/Augment_DemonicCleave`, chained with gaps up to 1.5 s while the skill runs, and `..._PhaseShard_Idle` on the player's pawn at start and end); the Reaper's tricks report no associated actor (they run on the echo). The mod keeps a skill window open for 3 s after each such begin or end. Skill script events (`GbxSkillScript:FireSkillEvent`, `K2_SkillStateBranch`, `GbxSkillTokenProviderStatics:AddToTokenStack`) fire for passives as well and carry no usable owner; not used.
- Token skills (`poc/probe_skills.py` + `probe_source.py` with the Rogue, 2026-09-20 22:4x): the Rogue's action skill runs no trick and fires no `FireSkillEvent`; its only signal is `/Script/OakGame.GbxSkillTokenProviderStatics:AddToTokenStack` (a static, no owner), called about once a second while the skill runs, with the token hits (`Fire`, unflagged, no explosion event) landing 1-2 s after each call. The same function fired throughout the Siren's Reaper, so it is treated as a general skill-activity signal (3 s window per call). Only the local player's skills run it in single player. Enemy grenades explode as `Proj_Order_Grenade` owned by the enemy character and are excluded by the instigator check.
- Character identity (`poc/probe_character.py`): `PlayerState.ActiveCharGuid` (four ints) differs per save and `ReplicatedCharacterDef` names the class (`Char_RoboDealer`, `Char_ExoSoldier`, `Char_DarkSiren`); `pawn.UXNameRepData.DisplayDef.Text` is the UI name ("Rogue", "Exo-Soldier"). `PlayerCharacterState` is empty.
- Grenade and melee hooks (call traces 2026-09-20 20:48): a grenade throw fires `/Script/OakGame.OakCharacter:ThrowGadget`, detonation fires `/Script/OakGame.GrenadeGadget:ExplodeCallback` and `/Script/GbxGame.projectile:Explode` (the Predator Drone gadget then fires missiles: `LightProjectileScript:OnImpact` per hit). A knife swing runs the offhand trick: `/Game/PlayerCharacters/_Shared/Tricks/Skills/Script_LTrick_HandleOffhand.Script_LTrick_HandleOffhand_C:OnBegin_Const` / `OnAnimNotify`. Non-gun damage landing shortly after one of these can be labelled grenade or melee. Not done in v1; the log keeps every hit as `other` with flags and damage type, so a later version can reclassify.
- Map changes and the widget: the engine pulls every viewport widget off the screen when a world is torn down. The mod destroys its widget (RemoveFromParent only if IsInViewport, then clear the keep-alive flag) as soon as the player controller disappears, and builds a new one when a controller with a pawn shows up.
- Crash on 2026-09-20 (character switch from the main menu, EXCEPTION_ACCESS_VIOLATION reading 0x1f, stack game -> unrealsdk -> pyunrealsdk -> python -> pyunrealsdk -> game): the first mod version re-fetched the player controller once a second and read through the cached wrapper in between. During the world teardown that wrapper pointed at freed memory and `Pawn` came back as garbage. Rule since then: fetch the controller fresh every tick (`get_pc()` is three pointer reads), compare by `_get_address()`, never keep a controller or pawn wrapper across frames, and wrap the hook entry point in a last-resort try/except. A vehicle pawn (`OakVehicle`) has no `EquippedInventorySlots`; reads of it must be tolerant.
- Weapon instance ids are not stable (sessions of 2026-09-20): `Item.data.InstanceId` is a process-wide counter. The Rogue's guns were 277/279/281/284 in every launch that continued with that character and 557/559 in the one launch where another character had been loaded first (the Siren's rifle was 287 after a direct load and 1149 after a switch from the Exo-Soldier). Every character switch in the menu therefore starts fresh weapon records. `poc/probe_identity.py` dumps the raw 216 bytes of `Item.data.Identity` (`InventoryIdentity`, no reflected fields) through ctypes at the struct's address inside the live weapon (the wrapper's `_get_address()` and the reflected offsets agree: Item +1000, Identity +1008). First run (2026-09-20 23:04): two shared object pointers at 0 and 8, five owned arrays (data pointers at 16/32/48/64/88, counts next to them: 12/11/11/9 elements, 0-1, 2-3, 8, 0), small ints at 176 (46/47/50/40) and 184 (47/47/63/47), and two high-entropy values at 200 (8 bytes) and 208 (4 bytes) that differ per gun and survive `GetIdentity()` by value: the seed candidates. Second run after a restart (23:12, new process): every non-pointer byte agreed for all four guns, only the owned-array pointers changed, and the Daedalus rifle went from InstanceId 390 to 280 while its bytes 200-211 stayed `97777d4239ef3f57 1e0637cf`. The mod keys weapon records on those twelve bytes as hex (`dmgtracker/itemidentity.py`); the instance id remains the per-launch cache key and the fallback identity (`instance:<n>`) when the layout check fails.
- Skill scripts (`poc/probe_actionskill.py`, RoboDealer, 2026-09-20 23:50): every action skill is a Blueprint `GbxSkillScript` (`SkillScript_Robo_Crossfire_C`, `SkillScript_Robo_Cleromancy_C`) whose `GetOwner()` is the player *controller* (not the pawn). Each action of the skill runs `/Script/GbxGame.GbxSkillScript:K2_StartSkillAction` (Crossfire: one per revolver volley every 0.35 s, the unflagged hits follow 0.1-0.2 s later; the dice skill: at the throw), the skill ends with `K2_StopSkillActions`; traits and tree passives (`TraitScript_Robo_Windfall_C`, `SkillScript_Robo_68_CriticalRole_C`) fire `FireSkillEvent` but no actions. The per-character libraries (`GbxSkillComponentFunctions_ActionSkill_*`) hold only helpers (cooldown, marks, stacks); `_RoboDealer` is empty. Token stack semantics, corrected: `AddToTokenStack` fires when the dice skill's tokens *return* (about six seconds after the throw, at the end of their hits), `ConsumeAll` when Crossfire spends the stack at its start and end. Hence the earlier half-Skill/half-Other split: the window opened late and closed early. The mod now opens the window on `K2_StartSkillAction` and lets every skill-credited hit extend it by 1.5 s. Flags seen on skill hits: 0x8 and 0x10 vary from hit to hit on the same target (likely which layer took the damage), so they are not a skill marker.
- Number formatting rule for everything shown to the user: Swiss style, `'` for thousands and `.` for decimals (`12'345.5`).
- `DamageType.ElementalType` is `EOakElementalType` (runner run 83, 2026-09-22): 0 noelement, 1 Corrosive, 2 Cryo, 3 Fire, 4 Shock, 5 Radiation; `unrealsdk.find_enum` returns the Python enum (no `_as_py`). The value is 0 on some elemental hits whose damage type name says otherwise (`Radiation`), so the dashboard takes the element from the type name first. The inventory calls kinetic `noelement` on a card and `impact` in its list.
- Runs 80-83 (2026-09-22, 25 minutes in the world, no menu opened yet): the item cards exist without any menu (a card at 0x2f9fcb720 held the gun in hand's name), the inventory list does not (no list record held any name), and a third model does: item records of about 700 bytes with the name at +32, the kind slug at +88, the rarity slug at +136, the manufacturer at +168, the element at +248, the picture path at +320 and the serial at +344, one for the gun in hand and one for the equipped grenade (6.4 KB apart) plus about forty for grenades not equipped (one arena at 0x36d04....). No seed within 2 KB of any, holders are the per-frame binding tables (changed within three minutes). Written up in `docs/item-names.md` ("The item records"), kept as `probe_run80_grenade_holders.py` to `probe_run83_hud_records.py`. The serial format is Nicnl's (`github.com/Nicnl/borderlands4-serials`); decoded, its first number is the item type and maps one to one onto the id's first four bytes, its other numbers never contain the id's remaining eight bytes (`poc/serial_decode.py`, a Python port of the decoder, checked all 25 serials of the table and six hash functions).
- The first four bytes of the item seed are a type hash shared by guns of one manufacturer and type (two Vladof SMGs both `134844c2`, the serials share their prefix too); the remaining eight bytes differ. The dashboard groups guns by it.
- Thumbnails (runs 78-79): `KismetRenderingLibrary.ExportRenderTarget` exists in the shipping build and writes an OpenEXR (ZIP-compressed half floats, lineOrder decreasing) for the RGBA16f `OakInventoryThumbnail_*` targets in 8 ms; `dmgtracker/thumbnails.py` decodes it with zlib and struct (`itertools.accumulate` for the predictor, a memoryview cast for the low bytes) in 0.25 s. `OakThumbnailManager.RenderedThumbnails` is a `TMap` pyunrealsdk cannot read (`MapProperty` unknown); its raw 24-byte elements are `{key: two int32 (0, n), value: the render target, hash links}`, the key not the instance id.
- Item names (probes `probe_names3.py` to `probe_names30.py`, 2026-09-21, written up in `docs/item-names.md`): a weapon name is a licensed-part prefix from the manufacturer's `*_LicensedPartPrefix_Table` (Borg magazine on a Jakobs gun = "Maintained"), an attribute prefix from the type's `OakWeaponNamingStrategy` thresholds over `weapon_damage`, `weapon_fire_rate`, `weapon_spread`, ... ("Screeching" = damage and fire rate over their first thresholds) and a title from the barrel's `InventoryNamingAspect`. The finished string is only kept by the UI, in three Coherent data models (probe runner runs 49-57, kept as `poc/probe_run49_around.py` to `probe_run57_slots_and_headers.py`): the slot records (288 bytes, type slug, rarity slug, identity copy with the seed at +248, slot order), the item cards (280 bytes, name, serial, rarity, damage text, slot order, in the same heap block as the slot records) and the inventory list (1072 bytes, seed at +632 with name, serial and slugs, a snapshot of the last inventory screen). Nothing an SDK object reaches points at them (their holders are the UI's binding caches), so `dmgtracker/itemnames.py` finds the inventory record by scanning for the equipped gun's seed and the cards by the shape of the node around their array header (`{ptr,1,1}` before `{data,num,max}`, `0` and `-1` after; runs 74-77). The anchor `OakGameInstance+704` of the first two sessions was heap adjacency and failed in session 3 (cards 104 MB away); the slot records next to the cards was adjacency too (hundreds of MB apart in session 5). A pointer scan run from Python finds its own needles: the `{4, type, 8, hash, address}` entries and `{type, address, ptr}` tables of runs 57-68 were `bytes` objects and other Python values (type pointers in `python314.dll`), not UI binding caches. A memory scan is fast when the buffer is not copied whole per region (`ctypes.string_at(buffer, got)`: 4.5 GB/s, 7.3 GB in 8 s; the 8 MB `buffer.raw` per 4 KB region made it 46 MB/s). `ReadProcessMemory` must never touch a guard page (it disarms it), so every read is preceded by `VirtualQuery`. Techniques that made this possible: a forged def pointer in a scratch struct gives typed SDK access to any Nexus definition (probe 14), a scratch Name field resolves raw FNames (13), `ReadProcessMemory` scans in a background thread do not freeze the game (21, 25), and `probe_runner.py` runs probes from `poc/inbox/` without the console. Dumper-7 and the forum's `GObjects`/`GNames`/`GWorld` offsets are the reflection globals the SDK already resolves; they do not reach the UI models (and Dumper-7's dumper thread asserts the engine: crash of 2026-09-21 22:23, `UObjectBase.cpp:153`).
